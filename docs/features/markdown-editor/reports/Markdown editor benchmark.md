# Papyro should decorate markdown, not replace it

The best markdown editor for Papyro keeps the markdown string as the only source of truth: a **CodeMirror 6 source editor with Obsidian-style live-preview decorations**, a **commonmarker 2.x (comrak) server renderer** shared by preview, publish and the public page, a pinned **"GFM + footnotes + GitHub alerts + Mermaid and math fences" dialect**, and an **agent interface built on exact-string `old_str`/`new_str` patches that land as pending, attributed suggestions** a human accepts hunk by hunk. The benchmark of roughly 25 products and 20 libraries shows a stable split. File-based writing tools (Obsidian, Typora, Bear's new Lettera, Zettlr, iA Writer) keep markdown canonical and win writers' loyalty. Block and WYSIWYG tools (Notion, Ghost, Substack, Medium) make rich cards easy but store proprietary models, and their round trips to markdown are documented as lossy. Doc-model editor libraries (TipTap, Milkdown, Lexical, BlockNote, MDXEditor) re-serialize markdown on every save. For a corpus that AI agents will diff and patch, that is a structural defect: the bytes the agent read are not the bytes the writer saved. Agents themselves push the same way. Notion's 2026 markdown API, Word's Copilot Agent Mode and TipTap's AI Toolkit all treat AI edits as reviewable proposals, and the most agent-friendly write shape is the same search/replace edit that coding agents use. **Before any editor work, Papyro must fix a confirmed stored-XSS issue** in its current Redcarpet pipeline. The same fix gives preview/publish parity, which is the foundation every later phase depends on. No existing Rails gem combines markdown storage, a professional viewer and editor, and agent review (Marksmith stops at a textarea with a preview, and Lexxy stores HTML), so the generic layers should ship as a **standalone open-source gem** with Papyro as its first consumer.

## Fix first: Papyro's renderer emits unsanitized HTML today

The current baseline is a plain textarea with Write/Preview tabs. Preview POSTs to `PapyroStudio::ArticlePreviewsController`, which renders with Redcarpet 3.6.1 + Rouge through `MarkdownRenderer` (`lib/markdown_renderer.rb`) and the `ActionText::Markdown` extension (`lib/rails_ext/action_text_markdown.rb`). That code path has **three confirmed defects**, all verified in the repository.

The first is stored XSS on the public site. `DEFAULT_RENDERER_OPTIONS` sets `filter_html: false`. `Articles::Presenter::Show#content_html` returns `MarkdownRenderer.build.render(content_markdown).html_safe`, and `app/views/articles/show/content.rb` outputs it with `raw`. No sanitizer runs anywhere on that path, so raw HTML written in an article body (script tags, `javascript:` links, arbitrary attributes) reaches every reader. The Studio preview does the same: `render html: preview_html.html_safe`. The second defect is attribute injection in images. `MarkdownRenderer#image` interpolates `url`, `alt_text` and `title` straight into `src`, `alt`, `title` and `data-lightbox-url-value` attributes without HTML-escaping, so a `"` in alt text breaks out of the attribute. The third is that the rendering paths disagree. `ActionText::Markdown#to_html`, used by `Articles::Operation::Publish` (`publish.rb:109`) and `Articles::Service::ContentAnalysis`, does run `Rails::HTML5::SafeListSanitizer`. A local run against rails-html-sanitizer 1.7.1 showed that its default allowlist **strips `table`/`thead`/`tr`/`td`, `input`, `figure`, `section`, `svg`, and every `id`, `aria-*`, `data-*` and `style` attribute**. So the HTML that Publish and content analysis derive differs from what the preview and the public page show.

The Content-Security-Policy in `config/initializers/content_security_policy.rb` is enforced, not report-only, and uses nonce-based `script-src`. That likely neutralizes inline `<script>` blocks, inline event handlers and `javascript:` URLs. It does not neutralize everything. The policy allows `script-src :self, :https`, so an injected `<script src="https://…">` from any HTTPS host is still permitted, as are injected forms, iframes (`default_src :https`), tracking images and inline styles. Because Papyro has multiple authors and roles, this should be treated as a real vulnerability and not as "authors are trusted".

The fix is the same work the editor needs anyway. Build **one canonical `render(markdown, locale:) → safe_html` service**. Render with raw HTML disabled: commonmarker's default `unsafe: false` scrubs raw HTML and dangerous links ([commonmarker](https://github.com/gjtorikian/commonmarker)). Then run one explicit allowlist sanitizer as the final step, adding tables, task-list checkboxes, heading/footnote `id`s, footnote sections, `figure`/`figcaption`, `details`/`summary`, alert classes and the lightbox `data-*` attributes. Escape or AST-build every interpolated attribute. Mark the output `html_safe` only after sanitizing. Then make the public presenter, the Studio preview, Publish and content analysis all call that service, and add regression tests with XSS payloads. Until this lands, a richer editor only makes more dangerous HTML easier to produce.

## Writers converge on "markdown underneath, rendering on top"

The market has settled on five editing paradigms, and the long-form evidence favors a specific compromise. **Raw source with styled syntax** is the iA Writer and Ulysses model. The **split pane with scroll sync** is used by StackEdit, Dillinger and HedgeDoc, and **Write/Preview tabs** by GitHub and Papyro today. **Inline live preview, which hides syntax except at the cursor**, is the model of Typora, Obsidian Live Preview, Bear 2 and MarkText. In **block WYSIWYG**, used by Notion, Craft, Google Docs, Ghost and Substack, markdown is only typing sugar. Obsidian is the clearest reference design. It offers Live Preview (the default), Source mode and Reading view per tab, and says Live Preview "often removes the need for Reading view" ([Obsidian Help](https://obsidian.md/help/edit-and-read)). Bear's developers announced Lettera in June 2026, a file-based Mac editor built on Bear 2's hide-syntax engine, with tables, MathJax math and CommonMark ([9to5Mac](https://9to5mac.com/2026/06/19/bear-app-developers-announce-lettera-a-beautiful-markdown-editor-for-mac/)). Well-regarded native editors are still investing in this paradigm.

Writer opinion splits, and both camps make good arguments. One Hacker News camp writes long-form in Typora and praises Bear for revealing markdown only around the word under the cursor. The other camp says "if you want Markdown, show the Markdown", because hidden syntax makes backspace unpredictable and causes layout jumps as markers appear and resize ([HN 41254936](https://news.ycombinator.com/item?id=41254936)). Proposed compromises include dimming markers iA-style, hiding syntax with a toggle, and never reflowing the line on reveal. One forum user asked for Typora-style hiding as an *option* in Obsidian, not a replacement ([Obsidian forum](https://forum.obsidian.md/t/a-wysiwym-typora-like-editing-mode/1953/38)). The safe product decision is to make the mode a per-user preference over the same text.

Three lessons come out of this evidence. First, **preview parity is the most cited trust signal**. Micro.blog reworked its preview to render tables and footnotes "to more closely match" the published blog ([manton.org](https://www.manton.org/2020/07/28/web-posting-markdown.html)), and Decap's raw-field preview is the most common complaint about it ([Lucky Media](https://www.luckymedia.dev/compare/tina-cms-vs-decap-cms)). Second, **lossy conversion is the most damaging failure**. Ghost moved its storage from Mobiledoc to Lexical JSON and converts old posts lazily when they are opened ([Ghost forum](https://forum.ghost.org/t/is-mobiledoc-removed-from-ghost/41949)), and Obsidian's own import guide tells users not to trust Notion's markdown export. Third, **no long-form competitor has native per-post translation**: Ghost, Substack and Medium all lack it. That makes Papyro's EN/ES model a real differentiator for the editor, not just a data concern. The baseline input set writers now expect is GitHub's: Cmd+B/I/K, paste a URL over a selection to make a link, drag/paste image upload, and `@`/`#`/`:` autocomplete ([GitHub Docs](https://docs.github.com/en/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax)). The delight features are Ghost's "paste a URL on an empty line to get a card" and iA's Focus mode and local Style Check, which flags fillers and clichés without rewriting them or altering exports.

## Source-of-truth libraries beat doc-model editors for an agent-edited corpus

The library landscape splits into two families, and the split decides most of Papyro's architecture. **Source-of-truth editors** (CodeMirror 6, Overtype, EasyMDE, Marksmith's textarea) treat the markdown string as the document and only decorate it, so the writer's bytes survive untouched. **Doc-model editors** parse markdown into a tree and re-serialize it, and their gaps are documented. TipTap's official markdown package is an "early release" that does not support comments and allows only one child node per table cell ([TipTap docs](https://tiptap.dev/docs/editor/markdown)). Its markdown export does not support footnotes, and a re-import gives back a simplified document ([TipTap export](https://tiptap.dev/docs/conversion/export/markdown/editor-extension)). Lexical's built-in transformers cover no tables, footnotes or task lists, and its docs warn that export can differ from input in escaping and bare URLs ([Lexical](https://lexical.dev/docs/packages/lexical-markdown)). Every open-and-save through such an editor can churn list markers, emphasis characters, escaping and table alignment. That produces noisy diffs and can silently drop reference links or footnotes, exactly the corruption a patch-based agent workflow cannot tolerate.

The strongest counter-argument comes from 37signals. They built House, a WYSIWYM markdown editor, for Writebook in 2024. When they tried it in another product in 2025 it "didn't fit", and they concluded "For most apps, WYSIWYG was just the right answer" before shipping Lexxy ([37signals](https://dev.37signals.com/lexxy-1-0/)). GitLab and Discourse both run ProseMirror WYSIWYG over markdown storage ([GitLab](https://docs.gitlab.com/development/fe_guide/content_editor/), [Discourse](https://meta.discourse.org/t/369779)). That steelman deserves weight, but Papyro is not "most apps". It is Writebook's use case (long-form, markdown-stored, Rails), plus agents that diff text. Both GitLab and Discourse also kept a raw-markdown mode and accept serializer normalization, which is a cost Papyro would pay on every agent round trip. The source-first design inverts theirs: rendering lives in decorations over the real text, so no mode switch can lose data. The weakness of that choice is that off-the-shelf CodeMirror live-preview packages are thin and stale, so **Papyro must build its own decorations** on the Lezer tree that `@codemirror/lang-markdown` exposes. It is the one significant engineering bet in this direction. A table-editing UI is the one feature that clearly favors doc-model editors. Source editors close the gap with "format table" and cell-navigation commands, which is the Zettlr 4 path.

Under importmap, CodeMirror is a multi-package ESM ecosystem, so cost is measured in pins, not bytes. The integration spike should record `bin/importmap json` and network totals and confirm that every package resolves to a single copy of `@codemirror/state` and `@codemirror/view`. If transitive pins resist that, vendor one pre-built ESM file. The Stimulus wrapper should keep the real `<textarea name="article[body]">` as the form value, sync into it on a debounce, and treat it as the rebuild source on reconnect. That is the same lazy-serialization pattern GitLab uses to avoid expensive get/set on every change ([GitLab](https://docs.gitlab.com/development/fe_guide/content_editor/)). The wrapper must also tear down cleanly across Turbo cache snapshots and morphs. React-based options (MDXEditor, BlockNote UI, Plate) are excluded: they would import a second view framework into a Phlex/Stimulus app.

## commonmarker 2.x and a pinned GitHub-compatible dialect

Papyro's renderer should move from Redcarpet to **commonmarker 2.x**, the Ruby binding to Rust's comrak. comrak passes **652/652 CommonMark 0.31.2 and 670/670 GFM spec tests**, and GitLab, crates.io and docs.rs use it ([comrak](https://github.com/kivikakk/comrak)). commonmarker shipped ten releases in 2026, the latest 2.10.1 on 2026-10-16, which fixed a native stack overflow on deeply nested input (GHSA-c4fj-h48v-9fxp) ([CHANGELOG](https://raw.githubusercontent.com/gjtorikian/commonmarker/main/CHANGELOG.md)). Redcarpet makes no CommonMark claim. Its last release was 3.6.1 in February 2025, and fixes for long-standing divergences (code-span precedence over links, escaped pipes in tables) sit unreleased on master ([redcarpet](https://github.com/vmg/redcarpet)). Those divergences matter because LLM output and other tools follow GitHub's parsing, not Redcarpet's. Speed is not a reason to stay. Redcarpet is roughly 3-4x faster, but commonmarker still renders a 2-10 KB article in milliseconds, and the output will be cached ([commonmarker README](https://github.com/gjtorikian/commonmarker)).

| Renderer | Spec compliance | Extensions relevant to Papyro | Raw HTML default | Speed (11 MB benchmark) | Maintenance |
|---|---|---|---|---|---|
| Redcarpet 3.6.1 (current) | No CommonMark claim | Tables, footnotes, fenced code; **no task lists, alerts, math, front matter** | Rendered (Papyro sets `filter_html: false`) | ~3-4x faster than commonmarker ([fork README](https://github.com/rossta/commonmarker)) | 1 release since 2023 |
| **commonmarker 2.10.x** | CommonMark 0.31.2 + GFM, full suites | Tables, task lists, footnotes, alerts, `math_code`/`math_dollars`, front matter, header IDs, syntect highlighting, AST walk, `to_commonmark` | Scrubbed (`unsafe: false`) | 4.5 iterations/s | 10 releases in 2026 |
| Markly | cmark-gfm (C) | GFM | Configurable | 15.6 iterations/s | n/v |
| kramdown | Own dialect | IALs, definition lists, abbreviations | n/v | ~40x slower than Markly | n/v |

Three migration hazards need explicit handling. commonmarker's `hardbreaks` **defaults to true**, unlike CommonMark, so set `hardbreaks: false`. Version 2.9.0 changed the heading-anchor markup, so pin it. Use `theme: ""` to emit CSS classes for code highlighting so Tailwind theme tokens can style it, or keep Rouge by walking `code_block` nodes ([commonmarker](https://github.com/gjtorikian/commonmarker)). The pipeline should mirror GitLab's Banzai design: parse, then AST passes, then HTML filters, then a database cache ([GitLab GLFM](https://docs.gitlab.com/development/gitlab_flavored_markdown/)). Concretely, Papyro would parse once, collect headings for the TOC, rewrite images into figures and the lightbox, tag Mermaid and math fences, add external-link `rel`, sanitize with the custom allowlist, and cache by content digest, locale and a `RENDERER_VERSION`. The Studio preview calls the same service and skips only the cache. Versioning the renderer avoids Dev.to's trap, where Liquid tags compile at save and stale HTML persists until an article is re-saved ([Forem](https://developers.forem.com/frontend/liquid-tags)).

The extended-syntax set should be what GitHub, GitLab, Obsidian and comrak all parse, because that is also what LLMs emit by default.

Server-side diagram SVG (mermaid-cli, which runs headless Chromium, or a self-hosted Kroki) is worth its operational weight only if diagrams must appear in RSS, email or OG images. The SVG must never pass through the article sanitizer. It should be generated in a job at publish time and served as an `<img>`. Spanish needs explicit work. comrak's smart punctuation targets English quotes, so locale-aware « » quotes and non-breaking spaces need a text-node pass keyed on `locale:`. Whether comrak exposes a locale option is unverified. CommonMark's emphasis-flanking rules around non-ASCII punctuation (the reason CJK bold fails in Obsidian, per [CJK Bold Fix](https://community.obsidian.md/plugins/cjk-bold-fix)) suggest testing `¿**Qué**?` and `¡**hola**!` cases. That inference has not been tested.

## Agents get exact-string patches that land as pending suggestions

Agent tooling has converged on a clear contract: **AI edits are proposals, not commits**. TipTap's AI Toolkit shows edits "as suggestions that users can accept or reject, in a Google Docs-style flow", and persistent tracked changes can attribute them to a named agent identity (`userId: 'ai-assistant'`) ([TipTap](https://tiptap.dev/docs/ai/ai-toolkit/client/agents/review-changes/tracked-changes.md)). Word's Copilot Agent Mode records its edits as tracked changes but "cannot … accept/reject tracked changes", so humans keep the approval step ([Microsoft](https://support.microsoft.com/office/agent-mode-in-word-647d5d14-eaec-4e8a-a574-7cefffa7f8f0)). Cursor's move from per-hunk to session-level review drew complaints from users who wanted "file by file, chunk by chunk" control ([Cursor forum](https://forum.cursor.com/t/bring-back-per-change-apply-inline-diff-review-you-re-throwing-away-your-best-ux-advantage/160856)). Papyro should therefore keep accept/reject at the hunk level. iA Writer adds the other half: accepted AI text stays shaded until a human rewrites it. Because iA stores that metadata inside the file, it gets misplaced when other apps edit the file ([iA](https://ia.net/writer/support/editor/authorship)), so Papyro should keep provenance in the database, not in the markdown.

| System | Edit granularity | Concurrency | Safety default |
|---|---|---|---|
| Notion markdown API (2026-03-11) | `old_str`/`new_str` patches, max 100 per call; whole-page replace ([Notion](https://developers.notion.com/reference/update-page-markdown)) | Generic 409 only | `allow_deleting_content: false`; unknown blocks returned as `<unknown>` |
| Google Docs API | Index ranges ([Google](https://developers.google.com/docs/api/how-tos/best-practices)) | `requiredRevisionId` optimistic lock, or `targetRevisionId` merge | None specific |
| TipTap Server AI Toolkit | Node hashes, chunked reads ([TipTap](https://tiptap.dev/docs/content-ai/capabilities/server-ai-toolkit)) | Yjs | Suggestions ephemeral unless Tracked Changes |
| Sanity Agent Actions | Schema paths | n/v | Never writes published docs by default; `noWrite` dry run ([Sanity](https://www.sanity.io/docs/agent-actions/agent-action-cheatsheet)) |
| Ghost Admin API | Whole post; HTML → Lexical "lossy" ([Ghost](https://docs.ghost.org/admin-api/posts/creating-a-post)) | `updated_at` | n/v |
| WordPress MCP adapter | Registered abilities as MCP tools ([repo](https://github.com/WordPress/mcp-adapter)) | Post locking | Abilities private by default |

Exact-string patches are the best fit for language models. The model copies text it has just read, an ambiguous match fails safely instead of corrupting the document, and concurrent edits don't shift addresses the way line numbers and indexes do. Markdown is also the cheap interchange format: Cloudflare measured one blog post at 16,180 tokens as HTML and 3,150 as markdown ([The New Stack](https://thenewstack.io/cloudflares-markdown-for-agents-automatically-make-websites-more-aifriendly)). The llms.txt convention (an `/llms.txt` index plus `.md` twins discoverable via `rel="alternate" type="text/markdown"`) gives published content a predictable agent-readable address ([llmstxt.org](https://llmstxt.org/)).

Safety is not optional. PromptArmor showed that **Notion AI saved document edits before user approval**: hidden white-on-white text made the AI insert an image whose URL carried private data, which leaked whether or not the user rejected the edit ([PromptArmor](https://www.promptarmor.com/resources/notion-ai-unpatched-data-exfiltration)). Simon Willison calls this combination of private data, untrusted content and an exfiltration channel the "lethal trifecta" ([Willison](https://simonwillison.net/2025/Sep/19/notion-lethal-trifecta)). Papyro's rules follow directly. Suggestions are truly pending, outside the live body. Remote images and links in a pending suggestion are rendered inert until accepted. Agent tokens are scoped to read, suggest or write, and never publish by default. Every call is rate-limited and written to an audit log. The existing Gemini translation output should flow through the same suggestion path. On the regulatory side, secondary sources report that EU AI Act Article 50 applies from 2026-08-02 and exempts AI-generated public-interest text that underwent human review under editorial responsibility ([virtuall.pro](https://virtuall.pro/blog/eu-ai-act-and-c2pa)). A recorded human acceptance step is therefore also a compliance asset. This should be verified against the legal text. C2PA for text is not yet dependable, so signed internal revision history is the practical provenance layer.

For transport, the **official `mcp` Ruby gem reached 1.0.0 on 2026-07-27**. It started at Shopify, conforms 100% to MCP 2025-06-18 and 2025-11-25, and offers a Streamable HTTP transport mountable as a Rack app, plus OAuth with PKCE ([MCP blog](https://blog.modelcontextprotocol.io/posts/ruby-sdk-1-0/)). Its mount pattern builds the server at boot and reportedly requires disabling reloading ([rubydoc](https://rubydoc.info/gems/mcp)), so a controller-based integration fits Papyro's dev loop better. ActionMCP targets Rails 8.1 + SQLite with consent-gated tools, but its claims are secondary-sourced ([mcp.so](https://mcp.so/servers/action_mcp)). No existing Rails gem ships a markdown editor with agent suggestion support, so this layer is open ground and has to be built.

## No Rails gem covers this, so build one

The Rails ecosystem solves markdown **parsing** well and markdown **editing** only at a basic level. No gem combines a safe rendering pipeline, a professional viewer, a professional editor and an agent review layer. The figures below come from the RubyGems API on 2026-11-03.

| Layer | Gem | Latest release | Downloads | What it is | What it lacks |
|---|---|---|---|---|---|
| Parse | `commonmarker` | 2.10.1 (2026-10-16) | ~99M | comrak binding: CommonMark + GFM | Library only: no sanitizer profile, viewer, styles, diagrams or math rendering |
| Parse | `redcarpet`, `kramdown` | Mature | High | Older parsers | Not CommonMark-compliant (Redcarpet) or its own dialect (kramdown) |
| Pipeline | `html-pipeline` | 3.2.4 (2026-01-06) | ~54M | GitHub's filter pipeline (sanitize, mentions, emoji) | A toolkit; every app assembles and secures its own pipeline |
| Templates | `markdown-rails` | 2.2.0 (2025-11-04) | ~0.66M | Renders `.md` view templates and partials | For developer-written templates, not user content |
| Editor | **`marksmith`** (Avo) | 0.6.0 (2026-08-14) | ~0.17M | GitHub-style textarea, toolbar, preview tab, Active Storage uploads | No live preview, diagrams, math, table tools, revisions or suggestions; a textarea architecture that caps how far it can go |
| Editor | **`lexxy`** (37signals) | 1.0.3 (2026-10-29) | ~1.09M | Polished Lexical editor for Action Text | Stores **HTML**, not markdown; markdown is only an input shortcut |
| Editor | `simplemde-rails`, `bootstrap-markdown-editor-rails`, `md_simple_editor`, `simple_form_markdown_editor` | Mostly 2017-era | <0.2M each | Asset-pipeline wrappers around JS editors | Abandoned or tied to dead JS (SimpleMDE's last release was 2016) |

37signals' House editor, the closest design to what Papyro needs, was never released as a gem. The download numbers are a demand signal. Lexxy passed a million downloads within weeks of 1.0, so Rails developers adopt a polished, Rails-native editor quickly. Marksmith's steady uptake shows a separate group that wants **markdown storage**. Nobody serves the intersection: markdown storage, editing quality comparable to Lexxy, and agents as reviewed co-authors.

**Why a new gem and not a Marksmith contribution.** Small improvements such as Mermaid in the preview could go upstream. The core of this direction cannot: a CodeMirror 6 editing surface, a sanitized and versioned rendering pipeline, and a suggestion data model. Each of those replaces part of Marksmith's architecture instead of extending it. A separate gem with clear prior art, credited in its README, is the cleaner path.

### What the gem provides

The gem ships four layers. Each works without the ones above it, so an app can adopt only the renderer, or the renderer and the viewer.

| Layer | Responsibility | Public API (illustrative; the gem name is still to be chosen, so `Md` stands in for it) |
|---|---|---|
| 1. Render core | commonmarker with `unsafe: false`; the pinned, versioned dialect (v1 GFM + footnotes + alerts + figures; v2 Mermaid + math fences); AST passes (heading anchors, TOC, figures, external-link `rel`); final allowlist sanitizer; locale hook for typography; cache key from digest + locale + `RENDERER_VERSION` | `Md.render(text, locale: :es) # => Md::Document(html:, toc:, headings:, word_count:, reading_time:)`; `Md.configure { _1.dialect = :v1 }` |
| 2. Viewer | Prose styles built on CSS variables (theme tokens; shadcn-compatible, so it looks native in chadcn apps and has sensible defaults elsewhere); code highlighting; lazy Mermaid 12 (`securityLevel: 'strict'`) and KaTeX via a Stimulus controller; heading-link and lightbox behaviour | `<%= markdown_view @post.body %>`; a Phlex component for Phlex apps |
| 3. Editor | CodeMirror 6 surface over the real `<textarea>` (the form value stays a plain field); Source → Live → Preview modes; toolbar and hotkeys; paste and drag uploads through Active Storage with an alt-text prompt; table commands; a `/` menu that inserts markdown; server preview from layer 1; Turbo-safe teardown | `<%= f.markdown_field :body, modes: %i[source live preview], uploads: true %>` |
| 4. Agent layer (optional) | Generator-installed revisions and suggestions tables; `old_str`/`new_str` proposals against a base revision; hunk-level accept/reject UI; inert remote URLs in pending suggestions; provenance (`author_type`, agent id, model); optional MCP tools through the official `mcp` gem; authorization through an app-supplied hook | `rails g md:suggestions`; `Md::Suggestion.propose(record, :body, edits:, base_revision:, author:)`; `<%= markdown_review record, :body %>` |

**Design rules that decide adoption.**

1. **ERB first, Phlex optional.** Most Rails apps use ERB, so the public surface is form-builder methods and view helpers. Internally the gem can render with Phlex, as chadcn does, and it also exports the components for Phlex apps such as Papyro.
2. **Both JS pipelines.** The engine ships importmap pins for CodeMirror (resolved to a single copy of `@codemirror/state` and `@codemirror/view`), the same way chadcn ships its pins. It also ships an npm package of the same Stimulus controllers for jsbundling and Vite apps.
3. **No storage opinion in the core.** The core works on any `text` column. Apps like Papyro and Writebook that keep markdown in a separate `ActionText::Markdown` record plug in through a small adapter. The core never creates database tables. Only the optional agent layer adds tables, through its generator.
4. **No authorization or AI-vendor dependency.** Agent permissions go through a hook (`authorize_suggestion { |user, record, action| … }`) that a Pundit, Action Policy or plain-Ruby app can implement. The gem defines the patch contract and MCP tools. It never calls an LLM itself.
5. **Secure by default and tested against hostile input.** An XSS payload corpus and the CommonMark/GFM spec examples run in the gem's CI. Raw HTML stays off unless an app opts in explicitly and accepts a documented risk.

**What stays in Papyro.** Editorial workflow (publish, schedule, trash), Mobility translations and the EN/ES side-by-side view, `Articles::Operation::*` and Pundit policies, the agent token model and audit log, the Gemini translation flow (which uses the gem's suggestion API), and the Studio layout. Papyro becomes the gem's first and most demanding consumer, the same relationship it has with chadcn.

**Repository setup.** The gem lives in its own repository under `doncan-orozco/`, with a sibling checkout made live in the host via `bundle config set --local local.<gem> ../<gem>`. The `flow` manifest (`.claude/workflow.yml`) gains it as a workspace repo, and its CI runs the spec suites, the XSS corpus and a dummy app with importmap and jsbundling variants. It ships under the MIT licence, which matches commonmarker, CodeMirror and Marksmith and keeps it usable anywhere.

## Recommended direction and phased roadmap

| Decision | Recommendation | Why |
|---|---|---|
| Editing paradigm | One markdown text, three per-user views: **Source** (styled, markers dimmed), **Live** (markers hidden off the cursor, reveal at element/word granularity without reflow), and a side-by-side **server Preview**. Ship Source first; make Live the default only after IME testing | Obsidian's model; resolves the hide-vs-show split; Live mode carries the IME and layout-jump risk ([Obsidian forum](https://forum.obsidian.md/t/issue-extra-latin-character-inserted-when-typing-japanese-ime-right-after-a-markdown-link/118859/4)) |
| Editor library | CodeMirror 6 + `@codemirror/lang-markdown`, custom Lezer-based decorations, wrapped in a `studio--` Stimulus controller over the real textarea | Byte fidelity, MIT, vanilla ESM, agent diffs map to CM transactions |
| Renderer | commonmarker ≥ 2.10.1, `unsafe: false`, `hardbreaks: false`, one service + custom allowlist + cache keyed by digest/locale/`RENDERER_VERSION` | Spec compliance, needed extensions, security fix |
| Dialect | "Papyro Markdown v1" = CommonMark + GFM + footnotes + GitHub alerts + figures; v2 adds Mermaid and `math_code`; versioned like Notion's `markdown_version` | What LLMs and GitHub/Obsidian/comrak share |
| Agent interface | Read: markdown + revision + headings; Write: `propose_suggestion` with `old_str`/`new_str` edits and `base_revision`; `apply_patch` for write-scoped tokens on drafts only, checked against `lock_version`; MCP via the official gem | Converged vendor contract plus Papyro's operation/Pundit rules |
| Collaboration | Optimistic locking + local backup now; comments before CRDT; Yjs (`y-codemirror.next`) only if demanded | WordPress pulled real-time co-editing from 7.0 |
| Packaging | A standalone, MIT-licensed Rails gem (render core, viewer, editor, optional agent layer) in its own repo; Papyro is its first consumer | No existing gem covers this; see the gem landscape above |

Placement now spans three repositories. **The gem** owns everything generic: the render service, dialect, sanitizer, viewer, editor, Stimulus controllers, the suggestion and revision tables (installed by its generator), the patch contract and the optional MCP tools. **The Papyro host** owns its domain: the operations that wrap the gem's APIs (`Articles::Operation::ProposeSuggestion`, `AcceptSuggestion` and similar, each a single intent), Pundit policies plugged into the gem's authorization hook, agent tokens, audit rows, Mobility translation flows, and the `.md` twins and `/llms.txt`. **`papyro_studio`** composes the gem's editor and review components into the Studio layout, together with the EN/ES side-by-side view.

| Phase | Priority | Scope |
|---|---|---|
| 0 | **Fix first** | One sanitized render service used by the public page, Studio preview, Publish and content analysis; escape image attributes; custom allowlist; XSS regression tests |
| 1 | **Must-have** | commonmarker migration with dialect v1 and a fixture corpus diffed against current output; CodeMirror Source mode with markdown highlighting, Cmd+B/I/K, paste-URL-on-selection, list continuation, image paste/drag through `ActionText::Markdown::Uploads` with an alt-text prompt; debounced side-by-side preview from the shared service; autosave with `lock_version` conflict detection and a local backup; word count and reading time; agent read endpoint and `propose_suggestion` writing pending, attributed suggestions; per-hunk accept/reject review in Studio; audit log, token scopes, `rate_limit`; Spanish dead-key/accent composition tests |
| 2 | **Should-have** | Live mode decorations (inline images, rendered tables, callout styling); Mermaid and math (lazy client, strict security); table commands (format, Tab between cells, insert row/column); callout/footnote/figure insertion via a `/` menu that inserts markdown, never remaps it; revision history with text and rendered diff; side-by-side EN/ES translation view with "source changed since translation" flags; MCP server via the `mcp` gem; `.md` twins + `/llms.txt` for published articles; paste-URL-to-embed; pre-publish checks (missing alt text, heading order); outline panel; focus/typewriter mode; locale-aware typography |
| 3 | **Later** | Paragraph-anchored editorial comments (WordPress Notes-style), with agents allowed to comment; authorship shading of accepted AI text; Obsidian foldable callouts; a local EN/ES style check that flags without rewriting; inline AI autocomplete (ghost text); server-side diagram SVG for RSS/email/OG; Yjs real-time co-editing; C2PA text manifests once the standard matures |

The phases map onto the gem's releases as follows. **Phase 0 lands in Papyro now** and does not wait for the gem. The XSS is live, and the sanitized render service written for it becomes the seed of the gem's render core, extracted once it is proven in production. **Phase 1 ships as gem 0.1**: render core, viewer and the Source-mode editor with uploads and preview. Papyro adopts it in place of its own service, and Phase 1's agent read and propose features land as the first slice of the agent layer. **Phase 2 ships across 0.x releases**: Live mode, Mermaid and math, table commands, revision diffs, the review UI and the MCP tools. The EN/ES translation view, `.md` twins, `/llms.txt` and pre-publish checks that are specific to editorial work stay in Papyro. A 1.0 release waits until a second, non-Papyro app (ERB, jsbundling) runs the gem. That proves the "ERB first, both JS pipelines" rules in practice and not only in a dummy app.

## Conclusion

The benchmark changes the question Papyro should be asking. Writers do not care which paradigm an editor uses. They care that what they type is what gets published, and that nothing they wrote silently disappears. Agents need the same guarantee in stricter form: a stable text they can read, patch by exact match, and have reviewed. A source-first editor with decorations is the one design that satisfies both audiences with a single data model. Every doc-model alternative needs a normalization layer between the agent's view and the writer's view, and that layer is where data loss happens. Papyro's real risk is not picking the wrong library. It is the custom live-preview layer, so ship Source mode first, earn trust with preview parity and agent review, and make Live mode the default only once Spanish composition and layout stability hold up in testing.

The less obvious takeaway is that Papyro's competitive gap sits in workflow, not in syntax. Ghost and Substack already render callouts and footnotes. None of them offers native per-post translation, a text diff between revisions, or a suggestion layer where an agent's edit is attributed, inert until accepted, and recorded as human-reviewed. Because Papyro already stores markdown, keeps translations through Mobility and routes mutations through operations, those differentiators cost little to build. The prerequisite is a single sanitized renderer, which is also the fix for the XSS exposure.

The same evidence supports packaging the work as an open-source gem. Rails has excellent markdown parsers and a polished HTML editor in Lexxy, but nothing that treats markdown as the stored document and gives it a professional viewer, a professional editor and a reviewed agent workflow. Building that as a standalone gem, with Papyro as its first consumer, costs little beyond what Papyro needs anyway. It also forces the generic parts to stay generic, and it puts Papyro's design in front of the whole Rails community instead of one app.
