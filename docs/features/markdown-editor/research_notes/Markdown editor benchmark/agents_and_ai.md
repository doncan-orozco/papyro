# AI agents as first-class co-authors of markdown documents (human + agent editing, review, provenance, Rails options)

Research date: 2026-11-03. About 25 searches and fetches. Primary vendor docs are preferred where they could be fetched. Points that came only from search snippets or aggregators are marked "(secondary)". Information that is stale, deprecated or moving is marked **[STALE/MOVING]**.

## 1. Inline AI UX in editors: how AI suggestions are shown and accepted

### Takeaway
The industry has converged on a pattern: **AI edits are proposals, not commits**. They are shown as Google-Docs-style suggestions or tracked changes, with per-change and bulk accept/reject. Lighter "ephemeral decoration" previews are the default in embeddable editor SDKs, and *persistent, attributed* tracked changes are a separate (often paid) layer. Code tools (Cursor) are moving from per-hunk inline diffs toward session-level review, and some users push back on that change.

### Cited Findings
- **Tiptap AI Toolkit (client)**: "Review Changes" shows AI edits "as suggestions that users can accept or reject, in a Google Docs-style flow". Features include an AI Agent Chatbot, tool streaming, selection awareness, a multi-document AI agent, and comments. Workflows include Insert content, Proofreader, "Tiptap Edit" (small and large edits) and Comments. The docs recommend the server-based AI Toolkit for most cases. The client toolkit suits fully in-browser setups. Both are paid add-ons on a private npm registry. — [Tiptap AI Toolkit](https://tiptap.dev/docs/content-ai/capabilities/ai-toolkit)
- **Tiptap: two review layers.** AI Toolkit "suggestions" are decorations that are "ephemeral and only visible to the current user of the document". By default, Toolkit methods "edit the document directly and not generate any suggestions". Persistent, shared review requires the separately licensed **Tracked Changes** extension. — [Tiptap review changes guide](https://tiptap.dev/docs/content-ai/capabilities/ai-toolkit/guides/review-changes) (secondary, via search snippet); [Tiptap review-changes (client)](https://tiptap.dev/docs/ai/ai-toolkit/client/agents/review-changes.md)
- **Tiptap Tracked Changes + AI**: set `reviewOptions.mode: 'trackedChanges'` on `toolkit.executeTool(...)`. Attribute the AI with `reviewOptions.trackedChangesOptions` → `userId: 'ai-assistant'`, `userMetadata: { name: 'AI' }`. Add `TrackedChanges` with `enabled: false` while the AI edits, so only AI edits are tracked. Users resolve with `acceptSuggestion`, `rejectSuggestion`, `acceptAllSuggestions`, `rejectAllSuggestions`. No server changes are needed. — [Tiptap tracked changes](https://tiptap.dev/docs/ai/ai-toolkit/client/agents/review-changes/tracked-changes.md)
- **[STALE/MOVING] Tiptap** previously shipped separate "AI Suggestion" (preview) and "AI Changes" (review after apply) extensions. They now sit under `/docs/ai/deprecated/...`. The docs tree also moved from `/docs/content-ai/...` to `/docs/ai/...`. — [AI Suggestion (deprecated)](https://tiptap.dev/docs/ai/deprecated/agent/review/ai-suggestion); [AI Changes (deprecated)](https://tiptap.dev/docs/ai/deprecated/agent/review/ai-changes.md)
- **BlockNote AI** (`@blocknote/xl-ai`, "early preview") streams responses. Users "accept or reject suggestions with a click", and AI actions show visual indicators ("Transparent Operations"). It is built on the Vercel AI SDK and works with any model (Llama, OpenAI, Mistral, Anthropic). "No Backend Required" (direct to the LLM or via your own infra). `xl-` packages are copyleft open source, and closed-source use needs a commercial (Business) license. — [BlockNote AI](https://www.blocknotejs.org/docs/features/ai)
- **BlockNote API**: the AI menu exposes `acceptChanges()`, `rejectChanges()`, `openAIMenuAtBlock`, `closeAIMenu` and `retry`. Version drift exists between the `AIExtension` class and `createAIExtension` factory names. — [BlockNote AI reference](https://www.blocknotejs.org/docs/features/ai/reference); [getting started](https://www.blocknotejs.org/docs/ai/getting-started) (secondary)
- **Liveblocks** positions 3.0 around "humans and AI working together". AI Copilots (GA after a private beta) can edit and comment inside an editor. Its SuperDoc example uses Yjs on Liveblocks with "suggestion mode for accepting or rejecting edits". A May 2026 update added AI agents in comment threads. Later announcements cover "sync engine APIs for agents" and a "Feeds" primitive, framing agents as native users. These are vendor claims. — [Liveblocks 3.0](https://liveblocks.io/blog/meet-liveblocks-3-0-the-fastest-way-to-let-your-users-collaborate-with-ai-in-your-product); [What's new May 2026](https://liveblocks.io/blog/whats-new-in-liveblocks-may-2026); [Unveil week recap: collaboration for humans and agents](https://liveblocks.io/blog/unveil-week-recap-realtime-collaboration-for-humans-and-agents) (secondary, via search summary)
- **Microsoft Word Copilot Agent Mode**: "Agent Mode will respect Track Changes, and if Track Changes is enabled then Agent Mode changes will be tracked". It "cannot turn on/off or accept/reject tracked changes". — [Microsoft Support: Agent Mode in Word](https://support.microsoft.com/office/agent-mode-in-word-647d5d14-eaec-4e8a-a574-7cefffa7f8f0). Roadmap item RM499428: Copilot asks clarifying questions, recaps actions and next steps after editing, and offers review controls in the canvas. GA target is February CY2026, for certain licenses only. — [M365 roadmap RM499428](https://mc.merill.net/message/RM499428). A Neowin report says Copilot now supports Track Changes natively, with edits visible by default. This is somewhat in tension with the support page, which only says Copilot "respects" tracking. — [Neowin](https://www.neowin.net/news/microsoft-words-copilot-just-got-much-smarter-at-handling-complex-edits/)
- **Google Docs Gemini**: I found no official Google doc saying Gemini writes native "Suggested edits". Third-party add-ons (e.g. "Redline AI Editor") insert AI changes as suggestions with per-edit or bulk accept/reject, and work with Gemini, ChatGPT and Claude. — [Workspace Marketplace: Redline AI Editor](https://workspace.google.com/marketplace/app/redline_ai_editor/885562230022)
- **Cursor (code-editor reference UX)**: per-change Accept/Reject still exists. In the new Agent Window, however, the default moved to *session-level Review*, and the Changes panel is "intentionally read-only right now" (staff reply). Users complain about losing "file by file, chunk by chunk" review. One summary lists per-change Keep/Undo plus file-level Keep File/Undo File in the editor, and a Git-style diff with file-level discard in the Agents Window. — [Cursor forum thread](https://forum.cursor.com/t/bring-back-per-change-apply-inline-diff-review-you-re-throwing-away-your-best-ux-advantage/160856) (community, secondary)
- **iA Writer Authorship**: AI text is greyed out, and text you change or replace turns black ("you have written it yourself"). Marking is manual ("Paste As > AI"). Writer does not detect the source automatically. It dims Apple Intelligence rewrites to show what the AI changed. Metadata sits at the end of the file: hidden in the editor, visible in other apps, and stripped on export to Markdown/HTML/PDF/Word. Editing in another app misplaces annotations, and Writer warns about it. — [iA: track authors and AI](https://ia.net/writer/how-to/track-authors-and-ai); [iA support: Authorship](https://ia.net/writer/support/editor/authorship); [iA: see what AI wrote](https://ia.net/topics/see-what-ai-wrote); [Matthew Cassinelli](https://matthewcassinelli.com/ia-writer-ai-authorship-markdown-annotations)

### Inferences
- Five display patterns appear: (a) **ghost text** for autocomplete (Tab to accept, Esc to dismiss; BlockNote has an autocomplete feature per a mirror, unverified); (b) **ephemeral decorations** for a single-user preview before applying (Tiptap default suggestions, BlockNote AI menu); (c) **persistent tracked changes** with an AI author identity (Tiptap Tracked Changes, Word Agent Mode, Liveblocks suggestion mode); (d) **side-by-side or git-style diffs** for whole-session review (Cursor Agents Window); (e) **authorship shading** (iA Writer) that shows *who wrote what* after acceptance, not *what is pending*.
- For an editorial app, (c) plus (e) fits best: pending AI edits are tracked suggestions attributed to a named agent identity, and accepted text keeps provenance metadata. The Cursor backlash suggests keeping **per-hunk** accept/reject, not only all-or-nothing.
- Tiptap and BlockNote both bundle AI into a proprietary rich-text model (ProseMirror JSON). A markdown-first Rails editor can still adopt their *UX contract* (suggest → review → accept per hunk) without their stack.

### Gaps
- Notion AI, Craft, Lexical/Ghost editor AI, Obsidian Smart Connections / Obsidian Copilot, and GitHub Copilot PR-description UX were not researched within the tool budget. From training knowledge (unverified): Notion AI shows inline proposals with Accept/Discard, Obsidian Copilot offers a chat pane with "apply to note" diffs, and GitHub Copilot generates PR summaries the user edits before saving. The report writer should not cite these without verification.
- Google's own documentation on whether Gemini in Docs emits native suggested edits was not found.

## 2. Agent-facing interfaces: edit granularity and concurrency

### Takeaway
2025-2026 brought a clear shift toward **markdown in/out with search-and-replace patches**, alongside full-document replace. Notion's markdown endpoint (`old_str`/`new_str`, the same shape as coding agents' edit tools) is the clearest example. Block-ID or node-hash targeting is used by rich editors (Tiptap, BlockNote, Notion blocks API). Concurrency is handled with revision IDs / optimistic locking (Google Docs, Confluence version numbers), CRDTs (Yjs in Tiptap/Liveblocks), or nothing explicit.

### Cited Findings
- **Notion Markdown API**: `PATCH /v1/pages/{page_id}/markdown`, `Notion-Version: 2026-03-11`. Modes:
  - `update_content` (recommended): array `content_updates` of `{old_str, new_str, replace_all_matches}`, max 100 operations per request. `old_str` must match exactly, and multiple matches fail unless `replace_all_matches` is set. Partial misses come back as `warnings` (`no_match`, `unsupported_tag`).
  - `replace_content` (recommended): whole page via `new_str`.
  - `insert_content` and `replace_content_range` are legacy and may be deprecated. They use an ellipsis selection `"start text...end text"`.
  - Safety default `allow_deleting_content: false` blocks deleting child pages or databases.
  - `allow_async: true` → 202 + `async_task`.
  - `markdown_version: "v2"` = "Notion-flavored Markdown" (recommended). v1 "enhanced markdown" is deprecated and will be rejected by the next Notion-Version.
  - Unloadable content appears as `<unknown>` tags, with IDs in `unknown_block_ids`. Pages over about 20,000 records have edit limits.
  - The page does not document conflict handling beyond a generic 409 `conflict_error`.

  — [Notion API: Update page markdown](https://developers.notion.com/reference/update-page-markdown)
- **Notion hosted MCP** at `https://mcp.notion.com/mcp` (OAuth). `notion-fetch` returns Notion-flavored Markdown, and `notion-update-page` edits properties and content. Sources disagree on the tool count (15 vs 18). StackOne says the hosted MCP "does not support block-level editing, so updates replace whole-page content". This may be stale given the newer `update_content` find/replace mode. — [developersdigest: Notion MCP](https://www.developersdigest.tech/mcp-servers/notion); [StackOne Notion MCP deep dive](https://www.stackone.com/blog/notion-mcp-deep-dive/) (secondary)
- **[STALE/MOVING]** The local open-source `makenotion/notion-mcp-server` (`npx @notionhq/notion-mcp-server`) is deprecated or unmaintained in favor of the hosted server. It had `retrieve-page-markdown` / `update-page-markdown` tools (full overwrite or targeted find-replace). — [mcpservers.org listing](https://mcpservers.org/zh-CN/servers/notion-mcp-server); [glama mirror](https://glama.ai/mcp/servers/J7suite/notion-mcp-server/tree) (secondary)
- **Google Docs API**: read with `documents.get` and save `revisionId`, then `batchUpdate` with `WriteControl`. `requiredRevisionId` makes the write fail if the doc changed (optimistic lock). `targetRevisionId` makes the server apply changes "against the collaborator changes" (operational-transform merge, new revision). If neither is set, the write applies to the current version. Edits use index-based requests (insertText / deleteContentRange with index ranges). — [Google Docs API best practices](https://developers.google.com/docs/api/how-tos/best-practices); [batchUpdate reference](https://developers.google.com/docs/api/reference/rest/v1/documents/batchUpdate?hl=de)
- **Tiptap Server AI Toolkit**: tool definitions come from `POST /v3/ai/toolkit/tools` (generic format, converted per provider), and execution goes through `POST /v3/ai/toolkit/execute-tool`. Edits target **node hashes** obtained from the read tool, or `"doc"` for the whole document, with replace / insert-before / insert-after. Client `tiptapReadChunks` splits large docs into chunks with a `Range` each, so only relevant sections are processed. Tool-name inconsistencies (`readDocument`/`editDocument` vs `tiptapRead`) appear in the docs. — [Server AI Toolkit](https://tiptap.dev/docs/content-ai/capabilities/server-ai-toolkit); [Tiptap Edit workflow](https://tiptap.dev/docs/content-ai/capabilities/ai-toolkit/workflows/tiptap-edit) (partly secondary; the tools reference URL returned 404 at fetch time)
- **Ghost Admin API**: native format is Lexical JSON. `POST /admin/posts/?source=html` (a query param, *not* a body field, which is a common pitfall) converts HTML → Lexical, "lossy", so rendered HTML may differ. For a lossless result, wrap HTML in an HTML card: `<!--kg-card-begin: html-->…<!--kg-card-end: html-->`. PUT updates also need `?source=html`. — [Ghost: creating a post](https://docs.ghost.org/admin-api/posts/creating-a-post); [Ghost forum](https://forum.ghost.org/t/ghost-api-html-text-body-empty/56402). (Ghost has no markdown input path except a markdown card. Not verified this session.)
- **WordPress**: the Abilities API is in core since WP 6.9. The official `wordpress/mcp-adapter` turns registered abilities into MCP tools/resources/prompts over REST or streaming transports. Abilities are **private by default** (`meta.public` / `meta.mcp.public` to expose). The default server offers discovery/info/execute meta-tools. Latest version seen is 0.7.0. — [WordPress/mcp-adapter](https://github.com/WordPress/mcp-adapter); [wordpress.org plugin](https://wordpress.org/plugins/mcp-adapter/?output_format=md)
- **Sanity Agent Actions**: `client.agent.action.patch` is **schema-aware** (validates paths/values against the uploaded schema, no LLM) with `target` paths and set/append/unset operations. Generate/Transform/Translate run LLM instructions (Translate takes a `styleGuide`). `noWrite: true` previews without writing. Agent Actions "never write to published documents by default" (`forcePublishedWrite: true` overrides) and skip `hidden`/`readOnly` fields. Patch is experimental. — [Sanity changelog](https://www.sanity.io/docs/changelog/45b74899-8911-4fb9-ba1e-9431fc6fcf0d); [Targets and paths](https://www.sanity.io/docs/agent-actions/targets-paths); [Agent Actions cheatsheet](https://www.sanity.io/docs/agent-actions/agent-action-cheatsheet)
- **Confluence / Atlassian MCP**: the official server's `updateConfluencePage` turns status macros into plaintext on update. This is a fidelity loss when round-tripping through a markdown-ish format. — [Atlassian dev community](https://community.developer.atlassian.com/t/atlassian-mcp-server-turns-status-labels-into-plaintext/98001). The third-party `mcp/atlassian` `confluence_update_page` takes a `content_format` of Markdown (default), wiki markup or storage format. Community servers require the current `version` number for updates (optimistic locking). — [Docker Hub mcp/atlassian](https://hub.docker.com/r/mcp/atlassian); [glama confluence-mcp usage](https://glama.ai/mcp/servers/@manateeit/confluence-mcp/blob/4c36f4f75a20ec287157e0e6d7c8d06d082c4e59/USAGE.md)
- **llms.txt + `.md` pages**: Jeremy Howard's proposal (2024-09-03, page updated 2026-08-10). `/llms.txt` has an H1 (the only required part), a blockquote summary, H2 link lists, and an "Optional" H2 section that agents can skip. Pages should serve a markdown twin at `page.html.md` or `page.md` (`index.md` for directories), discoverable via `<link rel="alternate" type="text/markdown">` or an HTTP `Link:` header. llms.txt is linked with `rel="describedby"`. "Thousands of sites" publish it, Mintlify autogenerates it, Chrome Lighthouse audits for it, and OpenAI/Anthropic/Gemini publish it for their docs. It is used mainly at inference time. — [llmstxt.org](https://llmstxt.org/)
- **Cloudflare "Markdown for Agents"**: content negotiation on `Accept: text/markdown`. The edge converts origin HTML to markdown and adds an `x-markdown-tokens` header so agents can check context fit. One example blog post went from 16,180 to 3,150 tokens (about 80%). Plan tiers are reported inconsistently (Pro+ / Pro-Business-Enterprise). A secondary source claims Claude Code and OpenCode send `Accept: text/markdown`. — [The New Stack](https://thenewstack.io/cloudflares-markdown-for-agents-automatically-make-websites-more-aifriendly); [PPC Land](https://ppc.land/cloudflare-cuts-ai-token-costs-by-80-with-markdown-conversion/) (secondary)

### Inferences
- Edit granularity, from coarse to fine:
  1. **Whole document replace** (Notion `replace_content`, Ghost PUT, Tiptap target `"doc"`). Simple, but it clobbers concurrent human edits and loses unsupported content.
  2. **Block/node ID or hash targeting** (Tiptap node hashes, BlockNote blocks, Notion block API).
  3. **Exact-string search/replace patches** (Notion `update_content`, mirroring Claude/Cursor `str_replace` edit tools). This is LLM-friendly because the model copies text it saw. It fails safely on ambiguity, and partial-miss warnings let the agent retry.
  4. **Index/range ops** (Google Docs). Brittle for LLMs.
  5. **Schema path patches** (Sanity `target` paths, JSON-Patch-like) for structured fields.
- For Papyro, a combination works well: `old_str/new_str` patches on markdown bodies, plus `requiredRevisionId`-style optimistic locking (`lock_version` in Rails), plus a "never write published" default (Sanity) and `allow_deleting_content: false`-style guards (Notion).
- Agents prefer patching via exact strings over line ranges, because line numbers shift with concurrent edits. Stable heading anchors or block IDs help for *addressing* (read a section, comment on a section), even when writes use string patches.

### Gaps
- GitBook (Git-sync markdown, change requests) and Linear (markdown issue bodies, MCP) were not verified this session. Contentful AI features were not researched.
- Notion's conflict semantics for concurrent human + API edits on the markdown endpoint are undocumented.
- CRDT-specific agent handling (an agent as a Yjs peer vs. a server-side apply) was mentioned by Liveblocks/Tiptap but not detailed in the sources fetched.

## 3. Why markdown is the LLM interchange format, its pitfalls, and addressability

### Takeaway
Markdown wins on token efficiency (about 80% fewer tokens than HTML in Cloudflare's measured example) and on models' native fluency with it. Every vendor, however, ships its *own dialect* (Notion-flavored v2, Ghost Lexical cards, Confluence storage format), and round-tripping loses non-markdown constructs (Confluence status macros, Notion `<unknown>` blocks, iA authorship metadata stripped on export).

### Cited Findings
- 16,180 → 3,150 tokens (about 80%) for an HTML → markdown blog post (single Cloudflare measurement). The `x-markdown-tokens` header supports chunking decisions. — [PPC Land](https://ppc.land/cloudflare-cuts-ai-token-costs-by-80-with-markdown-conversion/); [The New Stack](https://thenewstack.io/cloudflares-markdown-for-agents-automatically-make-websites-more-aifriendly)
- Dialect drift: Notion versions its markdown separately from its API (`markdown_version` v1 "enhanced" vs v2 "Notion-flavored"), with v1 to be rejected in the next API version. Unsupported content is returned as `<unknown>` tags plus `unknown_block_ids`. — [Notion API](https://developers.notion.com/reference/update-page-markdown)
- Lossy conversions: Ghost's HTML → Lexical is "lossy" unless content is wrapped in an HTML card ([Ghost docs](https://docs.ghost.org/admin-api/posts/creating-a-post)). The Atlassian MCP flattens status macros to text ([Atlassian community](https://community.developer.atlassian.com/t/atlassian-mcp-server-turns-status-labels-into-plaintext/98001)).
- Metadata inside markdown files is fragile: iA Writer stores authorship at the end of the file, visible in other editors, misplaced when another app edits the file, and stripped on export. — [iA support](https://ia.net/writer/support/editor/authorship)
- Addressability: llms.txt prescribes predictable `.md` URLs and `rel="alternate" type="text/markdown"` discovery. — [llmstxt.org](https://llmstxt.org/). Tiptap uses node hashes and chunk `Range`s so agents can target sections. — [Tiptap Server AI Toolkit](https://tiptap.dev/docs/content-ai/capabilities/server-ai-toolkit) (secondary)

### Inferences
- Papyro should pin one dialect (e.g. CommonMark + GFM tables/task lists + a small, documented set of extensions such as figures or callouts as fenced blocks or directives), version it the way Notion does with `markdown_version`, and return unsupported constructs as explicit placeholders rather than silently dropping them.
- Keep provenance and IDs **out of the markdown body** (DB-side or sidecar), because in-file metadata is fragile (iA experience). Expose heading slugs (stable `id`s derived from the original locale, persisted) for addressing.
- Tables and raw HTML are the riskiest constructs for round-trips and LLM output. Validate agent-submitted markdown server-side (parse → AST → reject or normalize).

### Gaps
- I found no rigorous benchmark comparing LLM edit accuracy across markdown vs HTML vs JSON document formats. Token figures come from a single vendor example.
- GFM table pitfalls (pipes in cells, alignment, no multi-line cells) are well-known but were not sourced this session.

## 4. Review and provenance: suggestions, attribution, history, approval, C2PA, disclosure

### Takeaway
Attribution works by giving the agent its **own author identity** inside the suggestion system (Tiptap `userId: 'ai-assistant'`, Word tracked changes under Copilot). Approval is enforced by defaulting agent writes to drafts or suggestions (Sanity: never write published by default). Text provenance standards (C2PA for text, EU AI Act Art. 50) are emerging but immature, and newsroom adoption is limited.

### Cited Findings
- AI author identity in tracked changes: `reviewOptions.trackedChangesOptions: { userId: 'ai-assistant', userMetadata: { name: 'AI' } }`. — [Tiptap tracked changes](https://tiptap.dev/docs/ai/ai-toolkit/client/agents/review-changes/tracked-changes.md)
- Word Agent Mode edits are tracked when Track Changes is on, but the agent cannot accept or reject. Humans keep the approval step. — [Microsoft Support](https://support.microsoft.com/office/agent-mode-in-word-647d5d14-eaec-4e8a-a574-7cefffa7f8f0)
- Draft-first default: Sanity Agent Actions never write to published documents unless `forcePublishedWrite: true`, and `noWrite: true` gives a dry-run preview. — [Sanity cheatsheet](https://www.sanity.io/docs/agent-actions/agent-action-cheatsheet); [Sanity changelog](https://www.sanity.io/docs/changelog/45b74899-8911-4fb9-ba1e-9431fc6fcf0d)
- Post-acceptance authorship (iA Writer): human-edited AI text flips to "yours" at the character level. — [iA how-to](https://ia.net/writer/how-to/track-authors-and-ai)
- C2PA and text: secondary sources claim C2PA 2.3 (Jan 2026) / 2.4 (Apr 2026) support embedded manifests in unstructured text and structured text such as Markdown/YAML, plus an "AI Disclosure" assertion. This is unverified against the spec. The more cautious view is that text provenance "relies on a combination of watermarking, author declaration, and detection tools, none of which is fully reliable". — [CASRAI GenAI disclosure 2026](https://www.casrai.org/news/genai-disclosure-scholarly-authorship-2026); [CASRAI glossary](https://casrai.org/dictionary/term/ai-provenance); [guptadeepak C2PA glossary](https://guptadeepak.com/guides/glossary/c2pa/) (all secondary)
- Newsroom adoption is limited. IPTC publishes C2PA FAQs and a Verified News Publishers List, and CBC/Radio-Canada plans C2PA touchpoints. — [INMA](https://www.inma.org/blogs/product-initiative/post.cfm/how-news-companies-can-prove-what-content-is-real); [IPTC media provenance](https://iptc.org/news/tag/media-provenance/)
- EU AI Act Article 50 (transparency) applies from 2026-08-02 per secondary sources. Deployers publishing AI-generated public-interest text must disclose it *unless* it underwent human review and someone holds editorial responsibility. This exemption is directly relevant to editorial apps. — [virtuall.pro EU AI Act and C2PA](https://virtuall.pro/blog/eu-ai-act-and-c2pa); [aivideobootcamp](https://aivideobootcamp.com/blog/ai-disclosure-compliance-2026-c2pa-eu-ai-act/) (secondary; verify against the legal text)
- Academic publishers: Elsevier requires AI-generated text to be reviewed and edited by authors, and forbids AI in peer review. Nature disallows AI images. — [CASRAI](https://www.casrai.org/news/genai-disclosure-scholarly-authorship-2026) (secondary)

### Inferences
- For Papyro: store a per-revision `author_type` (human/agent), `agent_id` / token id, model name and operation (e.g. the existing Gemini translation operation) on every write. Show agent suggestions as tracked changes under a named agent persona. Keep a human approval step before publish, which also supports the Art. 50 "human review / editorial responsibility" exemption. Optionally show a reader-facing disclosure ("translated with AI, reviewed by …").
- C2PA for text is not yet a dependable building block. Signed internal revision history is the practical provenance layer today.

### Gaps
- Primary C2PA spec text on text/markdown manifests was not fetched. Primary EU AI Act Art. 50 text was not fetched.
- News-publisher AI disclosure policies (AP, Reuters, etc.) were not found in this search.

## 5. Safety: prompt injection via document content, scopes, rate limits, audit logs

### Takeaway
Documents are an injection vector. The Notion AI incidents (2025) show the "lethal trifecta": private data, untrusted content and an exfiltration channel. A key flaw was that **AI edits were saved before user approval**, so an injected image URL leaked data even if the user rejected the edit. Mitigations are default-deny scopes, private-by-default capabilities, consent gates on tools, no auto-rendering of agent-inserted remote URLs, and a true pending state for suggestions.

### Cited Findings
- PromptArmor: Notion AI "AI document edits are saved before user approval". Hidden 1-pt white-on-white text made the AI insert a malicious image (URL carrying data) into a hiring tracker, and the data was exfiltrated whether or not the user accepted. The LLM-based upload scanner itself could be prompt-injected. Mitigations: disable workspace web search, avoid sensitive data in personalization. — [PromptArmor](https://www.promptarmor.com/resources/notion-ai-unpatched-data-exfiltration)
- Notion 3.0 agents (Sept 2025): a hidden-text PDF steered the agent to read client data and exfiltrate it via a crafted URL passed to the web-search tool. Willison calls this the "lethal trifecta" and suggests removing URL support from `functions.search()`. — [Simon Willison](https://simonwillison.net/2025/Sep/19/notion-lethal-trifecta). Notion reportedly remediated and upgraded detection, which is "improvement, not closure". — [Aviatrix summary](https://aviatrix.ai/threat-research-center/notion-2025-ai-prompt-injection-data-exfiltration) (secondary)
- WordPress abilities are private by default and must be explicitly flagged public for MCP exposure. — [WordPress/mcp-adapter](https://github.com/WordPress/mcp-adapter)
- ActionMCP: tools can declare consent. Those "require explicit user consent before execution", scoped to the session and revocable. — [mcp.so ActionMCP listing](https://mcp.so/servers/action_mcp) (secondary)
- Notion API: deleting child pages or databases is blocked unless `allow_deleting_content: true`. Updates need explicit "update content" capability (403 otherwise). — [Notion API](https://developers.notion.com/reference/update-page-markdown)
- Sanity: AI skips `hidden`/`readOnly` schema fields and never writes published documents by default. — [Sanity cheatsheet](https://www.sanity.io/docs/agent-actions/agent-action-cheatsheet)
- Official Ruby MCP SDK client implements OAuth (dynamic client registration, PKCE, scope handling), so a server can rely on spec-compliant OAuth clients. — [MCP blog: Ruby SDK 1.0](https://blog.modelcontextprotocol.io/posts/ruby-sdk-1-0/)

### Inferences
- Papyro rules:
  - Agent suggestions must be truly pending: not persisted into the live body, and remote images or links in suggestions not rendered or fetched until a human accepts.
  - Strip or neutralize hidden text such as zero-width characters and HTML comments in content passed to models.
  - Scope agent tokens per author or article, with read vs. suggest vs. write vs. publish permissions (publish never granted to agents by default).
  - Rate-limit per token (Rails 8 `rate_limit` in controllers).
  - Log every MCP/API call with token, tool, args hash and result to an audit table.
- Treat article content as untrusted input to the Gemini translation operation too. Translated output should go through the same suggestion/review path.

### Gaps
- No vendor-published rate limits for agent document APIs were collected (Notion's general API limits not fetched).

## 6. Rails-specific options: MCP servers in Ruby, ruby_llm, exposing documents to agents

### Takeaway
The **official `mcp` gem hit 1.0.0 on 2026-07-27**, supports spec revisions 2025-06-18 and 2025-11-25, and mounts in Rails as a Rack app. It is now the default choice. ActionMCP (a Rails 8.1 engine with consent, async tasks and DB-backed sessions) and fast-mcp (Rack middleware, `ActionTool::Base`) are alternatives. `rails_mcp_engine` glues fast-mcp to ruby_llm so one tool definition serves both MCP clients and in-app LLM calls.

### Cited Findings
- **`mcp` gem (official)**: 1.0.0 on 2026-07-27, the first stable release with a semver-stable API. It started at Shopify. Maintainers: Topher Bullock, Koichi Ito, Ateş Göral, Jonathan Hefner. Supports tools, resources, resource templates and subscriptions, prompts, completions, logging, pagination, progress, cancellation, and server→client sampling/elicitation/roots. Transports are stdio and Streamable HTTP. Client OAuth with DCR + PKCE. Implements MCP 2025-06-18 and 2025-11-25 (100% conformance), with 2026-07-28 support in progress. The Streamable HTTP transport is a Rack app that can be mounted in Rails routes. — [MCP blog: Ruby SDK 1.0](https://blog.modelcontextprotocol.io/posts/ruby-sdk-1-0/)
- Rails caveat for the official gem: the mount pattern builds the server at boot, so docs say `config.enable_reloading = false` is needed and you "must restart the server after changing tool or resource code". A controller-based integration is the alternative. — [rubydoc mcp gem](https://rubydoc.info/gems/mcp) (secondary via search snippet)
- **ActionMCP** (seuros): a Rails engine for production, network transports only (no stdio). Install with `bundle add actionmcp`, migrations and a generator. Subclass Prompt/Tool/ResourceTemplate. Supports MCP 2025-06-18 (backward compatible with 2025-03-26), consent-gated tools, async tasks with progress, and structured output. Requires Ruby 3.4.8+/4.0+, Rails 8.1.1+, and PG/MySQL/SQLite3. It matches Papyro's stack (Rails 8.1, Ruby 4.0, SQLite). — [mcp.so ActionMCP](https://mcp.so/servers/action_mcp) (secondary; verify on GitHub)
- **fast-mcp** (yjacquin): Tools + Resources, STDIO/HTTP/SSE transports, Rack middleware for Rails/Sinatra, Rails alias `ActionTool::Base` for `FastMcp::Tool`. SSE is the older MCP transport, so check for Streamable HTTP support. — [lobehub fast-mcp](https://lobehub.com/de/mcp/yjacquin-fast-mcp); [sourcepulse](https://www.sourcepulse.org/projects/2335330) (secondary)
- **rails_mcp_engine**: depends on fast-mcp ~> 1.6, rails >= 7.1 < 8.2, ruby_llm ~> 1.9. A "unified tool definition pipeline … using FastMCP and RubyLLM". — [rubygems rails_mcp_engine](https://rubygems.org/gems/rails_mcp_engine)
- **ruby_llm** (crmne): a unified Ruby LLM SDK. Its MCP-client capabilities were not confirmed this session. — [rubygems rails_mcp_engine deps](https://rubygems.org/gems/rails_mcp_engine) (indirect)

### Inferences
- Suggested Papyro agent surface. It mirrors the converged vendor APIs above. These are design inferences, not sourced facts.
  - **Read**: `GET /articles/:id.md` (and the localized twin per locale, the llms.txt `.md` convention) plus `Accept: text/markdown` negotiation. `/llms.txt` lists published articles. MCP resources `papyro://articles/{id}/{locale}`.
  - **MCP tools**: `list_articles`, `get_article(id, locale)` → `{markdown, revision, headings:[{slug, text}]}`, `propose_suggestion(id, locale, base_revision, edits:[{old_str,new_str}], rationale)` (creates pending tracked suggestions attributed to the agent and never touches the live body), `apply_patch` (same payload, write-scoped tokens only, fails on revision mismatch like Google `requiredRevisionId`, never on published content by default as in Sanity), `add_comment(anchor_slug|quote, body)`, `request_translation(id, to_locale)` wrapping the existing Gemini operation.
  - Each tool calls a `dry-operation` operation (fits Papyro's "mutations through operations" rule). Pundit policies apply on a token-backed principal. Writes go in a transaction with an audit row.
- The official gem is the safer long-term choice (spec conformance, stable API, OAuth). ActionMCP is attractive for Rails-native features (consent, DB sessions, async tasks), but its claims were secondary-sourced. The reloading caveat of the official gem's mount pattern matters for the Papyro dev loop. A controller-based integration avoids it.
- Papyro's existing Gemini translation can expose the same tool definitions in-app via ruby_llm (or the existing client), so in-app AI and external agents share one tool layer and one review pipeline.

### Gaps
- The `mcp` gem README Rails guide and the ActionMCP GitHub README were not fetched directly. Version numbers and the Streamable HTTP support of fast-mcp are unconfirmed.
- ruby_llm's own MCP client support and its tool DSL were not verified.
- No existing Rails gem was found that ships a markdown editor with built-in agent suggestion/tracked-change support. This appears to be an open niche (absence of evidence, limited search).
